# Cloud transcription

For live transcription with your own streaming provider key, see [Live cloud](live-transcription.md).

The personal app starts with local speech recognition and AI enhancement off. **Voice Engine** has three tabs, **Local**, **Cloud** and **Live cloud**. A tab only shows settings: browsing it does not change the engine dictation uses. The active engine is named above the tabs ("OpenRouter · Cloud", for example) and its tab title carries a check mark. With **Cloud**, the whole recording is uploaded to a speech provider after you stop.

## Providers and keys

Every key is entered in **AI Providers**: choose **Add provider**, pick the provider and paste its API key. Its row then shows what it can do (**Text**, **Cloud transcription**, **Live**) and a status: **API key missing**, **Not verified**, **Verified** or **Verification failed**. The one other place a key can be typed is the OpenRouter step of onboarding, which saves to the same entry. Saving a key sends nothing to the provider; it is contacted only when you verify, activate, test, refresh its models or use it. A key is only ever sent to its own provider.

| Provider | Speech model | Word timings | Also a text provider | How the audio is sent |
|---|---|---|---|---|
| OpenRouter | From its catalog (see below), default `openai/whisper-large-v3-turbo` | Per model | Yes | One request per chunk of at most 120 seconds |
| Deepgram | `nova-3` | Yes | No | One request per chunk of at most 780 seconds |
| ElevenLabs | `scribe_v2` | Yes | No | One request per chunk of at most 780 seconds |
| Mistral | `voxtral-mini-latest` | No | Yes | One request per chunk of at most 780 seconds |
| Speechmatics | `enhanced` or `standard` | Yes | No | A job per chunk, polled until done |
| Soniox | `stt-async-v5` | Yes | No | An uploaded file and a transcription per chunk, polled until done |
| AssemblyAI | `universal-3-5-pro` (with `universal-2` as its fallback) | Yes | Yes | An upload and a transcript per chunk, polled until done |
| Gladia | `solaria-1` | Yes | No | An upload and a job per chunk, polled until done |

A provider is one record with one key. A provider that offers several capabilities, such as OpenAI (Text and Live) or Mistral (Text, Cloud transcription and Live), is connected once and its key serves all of them; it then appears wherever one of its capabilities is offered, marked **Not verified** until a check has passed. Text verification (**Verify** on a text provider, a chat request) and speech verification (activating it in Voice Engine, a request without audio) are recorded separately, because a key can be valid for one and refused by the other.

### Keys saved before this version

Earlier versions kept the Voice Engine keys in their own Keychain entries (`openrouter-transcription` and `live-transcription.<provider>`). On the first launch of this version each of them is copied to its provider's entry in AI Providers when that entry is empty, so nothing has to be typed again and each feature keeps the key it used. When AI Providers already held a different key for the same provider (possible for OpenRouter and OpenAI), both are kept: text features keep the AI Providers key and Voice Engine keeps its own. The provider's row then shows **Two keys**, and its Manage sheet says that Voice Engine uses a different key, with **Use this key everywhere** and **Use the Voice Engine key everywhere** to settle on one. Saving a new key for that provider also replaces both.

A Live cloud provider chosen in an earlier version without a Voice Engine key never streamed: dictation ran on the selected local model. Its AI Providers key would now serve it, so the first launch of this version clears that choice instead, and dictation stays on the local model; the same applies to FluidMeet's Live cloud provider, and FluidMeet stays on Local. Activate the provider in Voice Engine to stream with it.

The old entries are left in the Keychain so that an older build still works after a downgrade, and a key saved later in AI Providers for such a provider is written to its old entry too. The new build never reads the old entries again once the copy has run: a key changed in an older build after that point is ignored, and has to be entered again in AI Providers. Keys for providers first connected in this version are not visible to an older build.

An older build knows only OpenRouter as a Cloud provider. With Cloud active on any other provider, an older build reads the setting as OpenRouter Cloud: it sends dictation to OpenRouter with OpenRouter's speech model and key, and fails with OpenRouter's missing-key error when it has no OpenRouter Voice Engine key (the `openrouter-transcription` entry). Activate a local model or Live cloud before downgrading to avoid this.

## Activating Cloud

1. In **AI Providers**, connect a provider that offers Cloud transcription.
2. Open **Voice Engine > Cloud**. The **Provider** menu lists the connected Cloud providers first; the active one is marked **Active**. Below a divider, every other Cloud provider appears as "<Provider>: set up…", which opens it in AI Providers. Choosing a connected provider only changes which provider's settings are shown.
3. The connection line shows the provider's speech status and **Manage in AI Providers**.
4. Choose the **Speech model**, and for OpenRouter the **Style model** (see [Two models](#two-models-chosen-by-the-cleanup-style)).
5. Choose **Activate**. The app first checks the key: for OpenRouter it lists the speech and style models this key can use, and the chosen models must be among them; every other provider gets one authenticated request without audio. If the check passes, Cloud becomes the voice engine with that provider and the button turns into a green **Active**. If it fails, the engine does not change and the row says why; for a rejected key it offers **Update key in AI Providers**.

**Use local model instead** on the active provider's row returns dictation to the selected local model. Activating a local model or a live provider also leaves Cloud. Removing the active provider's key in AI Providers returns dictation to the selected local model. With Cloud active and the key missing, dictation fails with the missing-key error; there is no automatic fallback, and the Voice Engine header says "<Provider> · Cloud. API key missing."

Speechmatics, Soniox, AssemblyAI and Gladia create a job and answer after a short wait, so dictation feels slower with them than with Local or Live cloud. They are still offered for dictation.

## Dictation with a provider other than OpenRouter

The recording goes to the provider's speech model. The transcript is then treated like local and Live cloud output: filler-word removal, the Custom Dictionary, spoken punctuation and finally your Cleanup Style, on the default text provider chosen in AI Providers. Cleanup Styles therefore need a verified text provider; the Cloud tab says so when none is verified. There is no 8-minute limit; that belongs to OpenRouter's style model. Dictation sends the language chosen in the overlay when there is one, and otherwise asks the provider to detect it; Soniox also receives the Primary and Secondary languages as hints. Deepgram, Speechmatics, AssemblyAI and Gladia offer only lists that restrict detection, which is stronger than a hint, so the preferences are not sent to them, and ElevenLabs and Mistral take no hints at all.

Recorded usage and cost exist for OpenRouter only. Every provider's Cloud tab links to its own usage and billing page. History records these dictations under `cloud-<provider>` (for example `cloud-deepgram`) with the model ID; OpenRouter dictation stays recorded as `openrouter`.

## Remote data at each provider

The app deletes what a job-based provider created for a transcription after the result is read, after a failure and when the transcription is cancelled, where the provider's API has a delete call. Deletion is best-effort: a failed delete is logged by kind (for example `kind=transcript`) and never fails the transcription, and a cancelled transcription does not wait for its deletes.

- **Speechmatics:** the job, which carries the audio, is deleted with `force`, so a job that is still running is stopped and removed as well.
- **Soniox:** both the transcription and the uploaded file are deleted, since stored files count against an account quota. Soniox refuses to delete a transcription that is still processing, as after a cancellation or a timeout; the app then tries again in the background, every 5 seconds for the first minute and every 15 seconds after that, for up to 10 minutes, and deletes the file once the transcription is gone.
- **AssemblyAI:** the upload goes with the job. Deleting the transcript also deletes the uploaded audio; AssemblyAI has no delete call for an upload on its own and removes one that never received a transcript after 24 to 48 hours. A transcript can be deleted only once it has finished, so a refused delete is retried in the background like Soniox's.
- **Gladia:** the upload also goes with the job. Deleting the job deletes the uploaded audio and the transcript; Gladia has no delete call for an upload on its own and refuses to delete a job that is still processing; the app retries that delete in the background like Soniox's. A job still unfinished after 10 minutes, or one left when the app quits during the retries, stays under Gladia's own retention.
- **OpenRouter, Deepgram, ElevenLabs and Mistral** answer in the same request and create nothing the app could delete; they keep request data under their own policies. Cloud requests to Deepgram carry `mip_opt_out=true`, as Live cloud requests do, which opts them out of Deepgram's Model Improvement Program; Deepgram then keeps the audio only as long as it needs to process the request. Deepgram's listed prices assume participation, and Deepgram has said that opting out forgoes a 50% discount, so a Deepgram request can cost up to twice the listed rate.

The Cloud tab's caption says the same: your recording is sent to the provider when you stop, and the provider may keep it under its own policy.

## OpenRouter

OpenRouter's key validation checks authentication and the supported speech and style models. Style models must support audio input, text output, and structured output. Validation cannot guarantee that your account permits a provider serving every listed model. For example, an account allowing only OpenAI, Anthropic, and Google cannot currently use the Whisper models served by Groq or DeepInfra. Review your own [OpenRouter provider permissions](https://openrouter.ai/settings/privacy) when the app reports that no provider is available. The app never changes these account restrictions, pins an underlying host, or silently switches providers.

### Model list

The speech model list follows OpenRouter's public transcription catalog. Once a key is saved, opening the Cloud tab with OpenRouter shown or the cloud meeting settings fetches the catalog at most once every six hours, and **Refresh models** always fetches it and checks which models this key can use. The request carries no credentials and no audio. The last fetched list is stored in the personal app's preferences, so it is available offline; a failed fetch keeps that list and is recorded in the debug log. A model OpenRouter withdraws disappears at the next fetch. A speech model selection pointing at it returns to the default model. A meeting selection stays visible as **no longer listed**, and meeting transcription reports that another model must be chosen. The three Whisper models (Large v3 Turbo, Large v3 and Whisper 1) and the two GPT-4o transcription models are built in and are always offered, even before the first fetch.

Being listed does not prove what a model can return. Word timestamps in particular vary by model and by the provider serving it, and the catalog does not describe them. The built-in Whisper models are documented to return word timestamps; OpenRouter serves Whisper 1 only through OpenAI, whose API documents word timestamps for it. Every other listed model is treated as plain text only until it passes the word-timing check described under [Completed meetings](#completed-meetings).

### Dictation

Dictation uploads audio after recording stops; it does not send cloud preview requests. Dictation detects any supported language automatically by default. Optional **Primary language** and **Secondary language** preferences are recognition hints where supported; they never restrict detection to those languages. During recording, the overlay offers Primary, Secondary, and **Detect automatically**. An explicit choice is remembered for later recordings; removing a selected language falls back to automatic detection. A dictation with a Cleanup Style supplies an explicitly selected language as an instruction to the style model; every other request sends it through OpenRouter's `language` field. Imported files also detect automatically and use both language preferences as optional recognition hints where supported. Each operation keeps its provider, model, hints, instructions, and credentials together; the overlay can update only the language choice of the recording in progress.

A dictation with a Cleanup Style sends language hints with the audio instructions. For the transcription endpoint, OpenRouter ignores top-level multipart `prompt` fields, so requests with hints use its documented JSON `provider.options` mechanism. Prompts are provided for OpenAI, Groq, and Together on the built-in models, without pinning a host or changing account permissions. DeepInfra prompt forwarding has not been verified and receives no prompt. Models that come only from the catalog have no verified prompt forwarding either, so they receive the explicit `language` field but no hint prompt. The serving provider may ignore hints; language coverage and mixed-language accuracy still depend on the model. See the [OpenRouter speech-to-text contract](https://openrouter.ai/docs/guides/overview/multimodal/stt).

#### Two models, chosen by the Cleanup Style

With OpenRouter shown, the Cloud tab has two model pickers, named by what they do. The **Speech model** turns speech into text; it serves dictation without a Cleanup Style, imported files, the local API and the command and rewrite modes, on OpenRouter's transcription endpoint. The **Style model** is used only when a Cleanup Style is on: after recording stops, the audio and the resolved style go to that model together on OpenRouter's chat endpoint, and it returns both the transcript and the styled text. There is no separate cleanup request and no dictation mode to choose. A line under the pickers says which model the next dictation uses. When the style resolves to **Off**, including through an app or shortcut rule, the recording goes to the speech model and the style model is not contacted.

The Style model list shows the newest audio-capable chat models OpenRouter offers, one per model family: models that accept audio input, return text and support structured outputs, refreshed together with the transcription catalog. Older generations, previews that have a stable successor, tool variants, batch variants, routers (OpenRouter's own and third-party ones, recognised by their variable price) and tilde aliases are hidden. Gemini Flash, Flash Lite and Pro come first. The default is the newest Gemini Flash listed; Gemini 3.8 Flash and Gemini 3.5 Flash Lite are built in for use before the first fetch or offline. A stored choice that is no longer offered, such as the deprecated Gemini 2.5 models, falls back to the default.

For a styled dictation the app inserts the styled text and stores both fields separately in history. The same model generates both fields, so the transcript is not an independent speech recognizer's reference or a guarantee of literal wording. App-specific rules, routing scope, and shortcut styles still determine the instructions sent. A previously selected Fluid Intelligence style uses the default cleanup instructions; its saved local preference is retained. No separate verified text AI provider is required to select, edit, or test a style. The Prompt Test editor sends its unsaved instructions with audio using the same one-request path and displays both returned fields without inserting text. Separate **AI Providers** remain available for text editing and other text AI actions.

A dictation with a Cleanup Style is limited to **8 minutes per recording**, because the whole recording travels in one request and OpenRouter caps audio input at 25 MB. A dictation without a style has no such limit: the speech model receives it in chunks of at most 120 seconds, like an imported file. A longer styled recording, unsupported model, malformed response, or provider failure reports an error; the app does not split the recording or automatically launch an extra cleanup, transcription, or local fallback request. Explicit retry starts another request. Import longer audio as a file instead, or turn the style off.

On a dictation failure, Voice Engine offers explicit **Retry and copy**, **Transcribe locally and copy**, and **Discard recording** actions. Retry uses the captured dictation settings with the current saved key. The failed recording stays in memory until retried, discarded, replaced by another failed recording, or the app exits. Local retry may need the selected local model to be downloaded. It never activates automatically. Cancellation stops requests and prevents delayed text insertion. The debug log records one line per failure naming the error kind (for example `server(400)` or `modelUnavailable`) and the model, never the transcript, audio, key or provider response.

## Imported files

With Cloud active, imported audio and video use the active provider's **Speech model**; File Transcription names the provider and model above the file and offers **Change**, which opens the Cloud tab. With Live cloud active, files use the selected local model. Dictation without a Cleanup Style, the local HTTP API's transcription endpoint and the command and rewrite modes use the same model; the local API reports it as "<Provider> / <model>". For OpenRouter the default is `openai/whisper-large-v3-turbo`; GPT-4o Transcribe, GPT-4o Mini Transcribe, and every other model in the transcription catalog are available for plain-text output. File transcription remains a speech recognition operation and does not send Cleanup Styles. Audio is converted to mono 16 kHz and uploaded in chunks of at most 120 seconds for OpenRouter and 780 seconds for the other providers. Requests requiring word timestamps use a one-second overlap and timestamp ownership to avoid duplicate words. Plain-text requests use non-overlapping chunks. Full decoded audio is currently held in memory, so very long imports can use substantial RAM even though each upload is bounded.

Completed file chunks are saved locally using an audio fingerprint and the complete transcription configuration. Retrying the same file and settings reuses completed chunks. Changing the model or language hints starts a distinct transcription. The cache contains transcript text and follows the personal app's local data backups. Short dictation does not persist this chunk cache.

## Completed meetings

FluidMeet's **Transcription** setting reads **Local**, **Cloud** and **Live cloud**. Cloud is OpenRouter for meetings, whichever provider the Voice Engine Cloud tab uses: recorded audio is sent to OpenRouter after you stop, with its key from AI Providers. Other cloud providers are not available for meetings yet; they reach meetings through Live cloud.

Meeting settings have a separate OpenRouter model selection, defaulting to `openai/whisper-large-v3`. The meeting pipeline aligns each word to a locally detected speaker turn, so the list only offers models with verified word timestamps: the three built-in Whisper models, plus any catalog model that passed the word-timing check on this Mac.

**Check catalog models for word timings** runs that check over every catalog model that has not been checked yet. The app synthesizes a four-second spoken phrase with the macOS system voice and sends that clip, never your audio, to each model with a request for word timestamps. Each model costs one ordinary billed request, two when the model rejects the timestamp request and the clip is retried as plain text; all of them appear in the recorded usage. A model that returns usable timestamps joins the list. A model that transcribes the clip without usable timestamps, or rejects the timestamp request while still transcribing plain text, is remembered as lacking them and stays hidden. Any other failure, such as a provider your account does not allow or an empty transcript, proves nothing and leaves the model unchecked; a rejected key, missing credits or rate limiting stops the run. Once every model has a verdict the button rechecks the refusals, so a provider that adds timestamps later can be picked up without an app update. Results are stored in the personal app's preferences. A passing check on a short clip shows the model can return timestamps; it does not guarantee them for every meeting chunk, so the runtime validation below still applies.

OpenRouter's own catalog notes name word-level timestamps for Whisper Large V3, Whisper 1, MAI-Transcribe 2, Qwen3 ASR 0.6B and 1.7B, Grok STT 1.0, Gemini 3.5 Transcribe, Fish Audio Transcribe 1 and 1 Pro, and AssemblyAI Universal-3.5 Pro, and its transcription guide names OpenAI, Groq, Deepgram, Mistral and Azure as endpoints that can return timestamps. Those notes are hints only; the check is what admits a model. AssemblyAI through OpenRouter accepts WAV only and at most 120 seconds per request, which meeting chunks and file chunks respect.

Local Nemotron still identifies speakers. Track separation, echo handling, speaker matching, and transcript assembly use the existing shared meeting pipeline.

Automatic and supported manual language selection apply to the completed cloud transcript. With OpenRouter, live captions run on this Mac in English; the **Live cloud** choice streams captions and the transcript from a live provider instead (see [Live cloud transcription](live-transcription.md#meetings-fluidmeet)). Missing or invalid word timestamps produce an incomplete result with an actionable error; the app never invents timestamps. Retrying a meeting can reuse successful recognition chunks with the same audio and frozen configuration.

Optional speaker labels for imported audio use local diarization aligned against one timed cloud transcript, so they also need a model with word timestamps. With OpenRouter the model's timestamps must be verified; the check runs from meeting settings with Cloud selected there and does not change the meeting model. The other providers document word timestamps for their models, except Mistral: with Mistral the file is transcribed without speaker labels, File Transcription says so in advance ("Without speaker labels."), and the transcript carries a note. Words with no confident speaker remain unassigned. Speaker labels for imported video are not supported in this release; disable that option to transcribe video as plain text.

## Meeting summaries

The personal build has no on-device summary model, so a completed meeting is summarized by the default text provider chosen in **AI Providers**, with the model chosen there and the key saved there. When no usable text provider is selected (none, Fluid Intelligence, or one without its key), the summary uses OpenRouter with the key Voice Engine sends to it and the selected Style model, because that key also authorizes OpenRouter's chat endpoint. While OpenRouter is the active Cloud provider, a selected OpenRouter text provider also uses the Style model. With neither available, the summary panel asks for an AI provider and links to AI Providers. The line under a summary names the provider and model and offers **Change**, which opens AI Providers.

Summaries run only when **Summarize** is pressed. The request sends the meeting title, date, duration, participant names and the speaker-labelled transcript, never audio, and streams the answer into the panel. Each summary type (executive, detailed, action items, decisions, participants, topics) has its own instructions; all of them tell the model to use only the transcript and to answer in the language the meeting was held in. A request is limited to about 400 KB of transcript text and ten minutes. A summary is saved next to the meeting and reappears for the same transcript, even after switching to another cloud model; editing the transcript or a speaker name hides it until it is regenerated. Cloud summaries do not pause dictation or unload local models.

## Text fidelity, costs, and privacy

Cloud recognition preserves the returned transcript. Dictation history stores optional styled text separately; styling remains off until explicitly configured. For dictation both fields come from the same generative model response. Recognition itself can still normalize numbers or punctuation. A literal transcript is not guaranteed by any model.

With OpenRouter, the Cloud tab shows recorded request costs and processing times, including dictation; the other providers report no cost, so the tab links to their usage and billing pages instead. Dictation requests charge for audio input and text output. Missing costs appear as **unknown**, and totals identify requests with unavailable costs. These are provider-reported amounts, not a billing guarantee. Cached chunks do not create new usage entries. Request diagnostics include metadata only, never API keys, audio bodies, or transcript content. Each request logs its upload size and duration, never its content.

Imported files, the local API, and command and rewrite recordings upload lossless FLAC, a fraction of the size of WAV. Dictation keeps WAV, because the chat endpoint it uses accepts WAV and MP3 only. The app keeps one connection to OpenRouter open during a recording so the request can start as soon as you stop.

Audio leaves the Mac only when a cloud operation is selected. Meeting summaries send transcript text, not audio, to the summary provider described above. The word-timing check sends only a synthesized phrase. The catalog fetch sends no audio, credentials, or settings, and does not run until a key is saved. Dictation also sends your selected instructions. App/window context and preceding text are sent only when the selected custom style enables context; they are omitted by default and in prompt tests. OpenRouter routes requests according to account eligibility and available providers. Its transcription endpoint does not currently honor per-request provider-pinning controls. Transcripts, styled text, resumable chunks, usage metadata, and recordings stay under the personal app's isolated local storage. See [maintenance and rollback](maintenance.md) for backup locations.

The public source build excludes the private Fluid Intelligence runtime. Existing optional external enhancement remains available. Direct OpenAI/Groq clients, custom speech endpoints, iPhone support, and public binary distribution are outside this release.
